# 功能开发与问题处理闭环

适用于开始一个实质功能、实现中遇到阻塞、或同一技术路线连续失败时。目标是尽快得到可验证、可维护且符合真实用户流程的结果，而不是在局部假设上反复试错。

## 1. 全局建模与根因诊断

先明确用户目标、正常用户流程、成功证据、风险边界和后续扩展影响。遇到问题时区分症状、直接原因和根因；先确认问题是否真正阻塞核心体验，再决定修正范围。

为本轮工作写出可证伪的路径：假设、最小安全改动、观测指标和停止条件。若前提不成立或路径会破坏长期边界，回到本步重规划。

## 2. 优先比对成熟方案

先查游戏或平台的原生机制、官方文档、可信开源实现、现有依赖和项目已有证据。比较其运行时前提、许可证、版本、风险和产品语义：

- 可以直接采用时，优先采用并补齐本项目的兼容与安全门禁；
- 只能借鉴时，提炼机制与契约，不复制未经许可的代码或数据；
- 若成熟方案暴露当前路径假设错误，立即回到第 1 步调整路线。

检索应聚焦会改变方案选择的信息；已有可信本地证据足够时，不为了形式重复联网搜索。

## 3. 有界、批量且尽量自动化的验证

没有适用成熟方案时，再实施本地验证。每条技术路线默认进行 2–4 次有区分度的尝试；每次只改变一个关键变量，并保留能够支持或否定假设的证据。

优先把互不依赖的假设、样本和状态组合并为一次安全的批量实验。自动化应覆盖可重复的构建、静态检查、运行时采样、归档和分析；只把无法安全自动化且确实需要人的感知判断留给用户。不得用自动化绕过权限、安全门禁或真实用户选择。

出现强反证、风险不可接受或原生稳定性受损时，应提前停止该路线，不机械完成次数。若失败主要来自多步骤验证而非路径错误，重构验证流程以减少人工操作和部署轮次。

## 4. 回顾全局并收敛

重新诊断阻塞来源：路径错误、实现缺陷、证据不足、环境限制，还是产品需求本身需要调整。选择继续、切换成熟方案、降级为安全只读能力、暂缓，或拆分后续研究；不要在已证伪路径上继续堆补丁。

沉淀结论：更新架构边界、测试、证据和路线图，明确已验证范围、未覆盖项和下一步。对用户报告结论与需要其参与的最小验证动作，而不是暴露无价值的试错细节。

## 使用边界

- 此 Skill 提供研发决策流程，不替代项目专属安全规则、许可证要求或发布流程。
- 小型、低风险、已知修复可直接实施；不要把四步流程形式化地套在每个拼写修正上。
- 高风险、不可逆或外部影响操作仍需遵循相应授权与安全约束。
