# 功能开发与问题处理闭环

适用于开始实质功能、实现中遇到阻塞，或同一路线连续失败时。目标是得到符合真实用户流程、可验证且可长期维护的结果。

## 1. 开始前先看全局

明确用户真正要完成的任务、正常用户流程、核心价值、成功证据、风险边界、当前架构与后续扩展。规划从现状到目标的最短可靠路径，避免直接陷入局部实现。

遇到问题时，先区分症状、直接原因和根因。写出当前假设、支持与反对证据、观测指标和停止条件；需要修正的是根因，而不只是表面现象。若基础前提不成立，重做路径规划。

## 2. 第一轮成熟方案检索

编码或试错前，先检查项目已有证据和依赖，再检索官方文档、平台或游戏原生机制、可信开源实现、社区成熟方案和逆向资料。对比当前卡点，并判断：

- 可直接采用：复用方案，并补齐本项目的兼容、安全和验收门禁；
- 可参考机制：提炼原理、接口和证据边界，不复制许可证不允许的代码或数据；
- 前提或目标不同：记录不适用原因，进入本地验证；
- 暴露路线错误：立即回到第 1 步重规划。

检索只收集会改变方案选择的信息。技术问题优先使用官方、源码和一手逆向证据；时效性或外部事实可能变化时必须联网核实。

## 3. 有界实现与验证

没有可直接采用的方案时，进行 2–4 次有区分度、可证伪的尝试。每次只改变一个关键假设，并保留能够支持或否定它的证据。强反证、不可接受风险或原生稳定性受损出现时立即停止，不机械凑次数。

优先批量覆盖互不依赖的假设、样本和状态组合。把构建、静态检查、运行时采样、归档与分析尽量自动化；只把无法安全自动化且确实需要人的感知或业务判断留给用户。自动化不得绕过权限、安全门禁或用户选择。

## 4. 失败后先分类，再决定下一步

2–4 次仍未达到目标时，不直接继续试错，先判定阻塞类型：

- 路径或基础假设错误：回到第 1 步，重新规划；
- 实现缺陷已定位：修正后执行最小回归验证；
- 路径合理但验证链过长：重构为批量、并行或可恢复的自动验证，减少部署和人工轮次；
- 证据仍不足或失败机制未知：带着已有反证进行第二轮定向检索，查找能解释当前失败的成熟实现、源码或原生机制，再决定复用、换路或设计下一组实验。

第二轮检索不是重复第一轮关键词，而是使用已观测的对象、错误、状态转换和失败边界缩小问题。

## 5. 最后再次回到全局

检查结果是否真正改善用户体验、是否符合正常人的操作逻辑、是否解决根因、是否支持未来扩展，以及代码和验证成本是否合理。根据证据选择继续、换方案、降级、暂缓或拆分研究；不得在已证伪路线之上继续堆补丁。

将结论沉淀到代码边界、测试、证据和路线图：明确已验证范围、未覆盖项、停止原因及下一步。向用户报告结论和必要的最小参与动作，不转嫁可自动完成的重复操作。

## 使用边界

- 此 Skill 不替代项目专属安全规则、许可证、领域资料优先级或发布流程。
- 小型、低风险且修复路径明确的改动可直接实施，不必机械展开完整流程。
- 高风险、不可逆或外部影响操作仍需遵循相应授权与安全约束。
